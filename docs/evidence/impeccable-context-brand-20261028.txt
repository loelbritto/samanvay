# PRODUCT.md

# Samanvay

Samanvay is a clearly labelled student prototype for institutional complaint coordination. Its people, institutions, complaints, policies and integrations are synthetic demonstrations. It has no official AICTE connection.

## Users and work

Officers find complaints, review evidence and record the next action. Supervisors assign owners and exercise explicitly delegated powers. Coordinators agree institution plans across bureaus without taking over case ownership. Management sees its authorised scope. Administrators maintain demonstration accounts without acquiring complaint access.

The first screen should help an officer choose what to work on. The user reported too many controls and technical terms and asked for a professional redesign, delegating implementation choices. Prefer plain labels, a calm work queue, obvious ownership and progressively disclosed secondary actions. No standing aesthetic preference beyond this has been confirmed.

## Invariants

Preserve every complaint and original submission. Institution identity, complaint relationship, complaint ownership and coordination responsibility are separate concepts. Persistent database state backs workflows; optimistic versions, scope checks, audit events and outbox jobs remain authoritative. Automated relationship output is a suggestion requiring authorised human review; it never merges records or decides outcomes.

## Platform and limits

Local web app: React, TypeScript, Vite, FastAPI and SQLAlchemy, with SQLite and private evidence files. Keep the existing databases intact. Production hosting, official integrations, real notification delivery and validated ML accuracy are outside the demonstrated implementation. Browser acceptance requires actual rendered evidence; code checks cannot substitute for it.

# Design System: Samanvay

## Overview

**Creative North Star: "A Civic Records Desk in Daylight"**

A civic records desk in daylight: deep ink navigation holds the workspace together, while white work surfaces and quiet dividers keep records easy to scan. This is an operating interface with familiar controls, direct labels and a restrained visual hierarchy.

The system gives actions and state changes visible emphasis without turning every fact into a separate card. A single system sans family, aligned rows and explicit responsibility support sustained administrative work. Secondary choices use native disclosures; prototype identification remains visible.

This is a source-derived record of the replacement system in `frontend/src/design-system/tokens.css` and `workspace.css`, sampled against the workspace shell, sign-in form, queue, record rows and shared components. The direction was delegated, not approved through a visual comp. Visual acceptance is **OPEN**: saved browser policy blocked capture, and desktop/mobile screenshots, keyboard review and 200% zoom review are still missing. Reviewer disposition remains **recapture**. The manual detector returned no findings (`[]`); that result does not establish rendered acceptance.

**Key Characteristics:**

- Deep ink navigation, paper-white work surfaces and cool neutral spacing.
- One system sans family with compact headings and readable form controls.
- Blue actions and selected states; textual status labels accompany semantic color.
- Flat panels, thin separators and modest corner rounding.
- Responsive rows and grids, with collapsible navigation on narrow screens.

## Colors

Cool ink and slate neutrals support restrained blue interaction, with pale semantic washes used for status and notices. The frontmatter is normative; the names below describe the same tokens without introducing alternative values.

### Primary

- **Action Blue** (`action-blue`): primary buttons, links, selected filters and selected review items.
- **Selection Blue** (`selection-blue`): selected review-item fill and informational message fill.
- **Action Hover** (`action-hover`): primary-button hover state.
- **Focus Blue** (`focus-blue`): keyboard focus outline, independent of selected state.

### Secondary

These are semantic communication colors, not a second decorative accent.

- **Attention Amber / Attention Wash** (`attention-amber`, `attention-wash`): attention badges and amber notices. The current record-row implementation applies amber to “Awaiting information”; row-level overdue coloring is not established.
- **Success Green / Success Wash** (`success-green`, `success-wash`): the shared positive badge variant.
- **Error Red / Error Wash** (`error-red`, `error-wash`): form and connection validation summaries.

### Neutral

- **Ink** (`ink`): primary text and navigation rail.
- **Slate** (`slate`): secondary controls, labels and neutral badges.
- **Muted Slate** (`muted-slate`): supporting descriptions, captions and inactive filters.
- **Divider** (`divider`): panel edges, row separators and section boundaries.
- **Soft Slate** (`soft-slate`): neutral badges, count chips, avatars and secondary-button hover.
- **Canvas** (`canvas`): page background and queue context bands.
- **Paper** (`paper`): panels, fields, top bar and inverse text on solid actions.
- **Rail Text / Rail Selected** (`rail-text`, `rail-selected`): navigation text and current destination.
- **Field Border** (`field-border`): the stronger edge on inputs, selects and textareas.

The sidecar's tonal ramps are synthesized preview aids. They do not extend the implementation palette.

**The Action Accent Rule.** Use blue for actions and selected states. Pair attention, success and error colors with explicit text that explains their meaning.

## Typography

**Headline and Body Font:** Segoe UI, with Helvetica Neue, Arial and sans-serif fallbacks.

**Character:** A familiar system sans supports operating speed and legible controls. The same family carries titles and records; there is no separate display face or decorative typography.

### Hierarchy

- **Headline** (`headline`): page titles. The compact variant is used on sign-in and at the narrow-screen breakpoint.
- **Title** (`title`): section headings.
- **Small title** (`title-small`): tertiary headings. Record subjects use the same size and weight with a more open line height (1.45).
- **Body** (`body`): general prose and field values. Introductory page copy is capped at (72ch).
- **Label** (`label`): buttons and form labels; sentence case.
- **Supporting** (`supporting`): captions, secondary record detail and account context.
- **Badge** (`badge`): compact textual status indicators. Counts use tabular numerals.

There is no uniform geometric type ratio. Size steps reflect the operating hierarchy in the source. The smaller brand subtitle and record-reference styling in the build are not promoted into a general reusable type role; their legibility remains part of the open rendered review.

**The One Family Rule.** Use the same system sans stack for headings, navigation, forms and body text. Build hierarchy with size, weight and spacing.

## Layout

The wide-screen shell uses a fixed navigation rail (224px), an account bar and a main workspace capped at (1600px). Main content starts with horizontal and top padding (32px). The sign-in view is a centered column capped at (504px).

Reusable layouts are explicit grids and flex rows. Two-column forms and institution lists use gaps (20px); detail, evidence and review layouts commonly use gaps (24px). The spacing tokens form a (4px) base rhythm, while source component padding also uses fitted values such as (9px 14px) for buttons and (22px 20px) for records.

Responsive behavior is implemented at these maximum widths:

- **1250px:** record next steps move below the main row; the review navigation narrows.
- **1050px:** detail and review content becomes one column; review items and some filters become two columns.
- **800px:** the fixed rail becomes an in-flow header with a menu disclosure; workspace inset is removed and main padding becomes (24px 20px 0).
- **560px:** records place the subject above owner/status and the next step below them; most form and evidence layouts become one column; panel padding becomes (20px 16px).
- **360px:** main horizontal padding becomes (12px), and the remaining compact account and summary grids stack.

Records and controls allow wrapping rather than fixed-height clipping. The styles include a print layout that removes navigation, account context and the footer. These are implemented rules, not rendered test results.

## Elevation & Depth

The implemented system has no box-shadow vocabulary. Surface fill, one-pixel edges and separators create depth. The dark rail establishes the frame; white panels remain flat against the cool canvas. Selected states change fill or underline rather than lifting.

**The Flat Surface Rule.** Separate resting surfaces with fill and borders. Do not add decorative shadows to panels or controls.

No decorative transitions or animations are defined. The reduced-motion media rule explicitly disables animation and transitions and restores automatic scrolling.

## Shapes

Panels have modest rounded corners (`panel`), controls use a tighter radius (`control`), notices use an intermediate radius (`notice`), and badges use the smallest rounding (`badge`). Borders are generally (1px). Filter and detail-navigation selection uses a bottom edge (2px) with square tab corners. Circular avatars and timeline dots are the limited recurring circular forms.

Icons are inline outline SVGs with rounded caps and joins; the shared default uses a (24 × 24) viewBox, a (20px) rendered size and a stroke (1.6). Icon size follows context. Text remains the primary source of meaning.

## Components

### Buttons

Quiet, familiar controls with a clear primary action.

- **Shape and spacing:** control radius, inline alignment with an icon gap (8px), padding defined by the frontmatter and minimum height (44px).
- **Primary:** Action Blue with Paper text; Action Hover on hover.
- **Secondary:** Paper with Slate text and a Divider border; Soft Slate hover. The source's secondary class relies on this shared default button style.
- **Text:** transparent background and border with Action Blue text; shared hover adds Soft Slate.
- **Focus:** solid Focus Blue outline (3px), offset (3px).
- **Disabled:** muted text on Soft Slate, Divider border and a not-allowed cursor. No additional active-state animation is defined.

### Chips

Compact status labels and counts, not substitute buttons.

- **Status:** neutral, blue, amber and green variants share the same badge shape and padding.
- **Count:** compact neutral fill, tabular numerals and a minimum width (24px).
- **Meaning:** status text remains visible with the color. Badges are noninteractive and carry no invented hover or focus state.

### Cards / Containers

Flat, bordered work surfaces.

- **Shape:** panel radius, Paper background and a Divider edge.
- **Padding:** the standard padded surface uses the panel frontmatter padding; narrow screens use the Layout override.
- **Depth:** use the Flat Surface Rule. Individual record rows are separated inside a shared panel instead of receiving separate shadows.

### Inputs / Fields

Standard browser controls made consistent with the workspace.

- **Style:** Paper surface, Ink text, Field Border edge, control radius and a minimum height (44px).
- **Labels:** visible labels above controls, using the label type role.
- **Focus:** the shared Focus Blue outline. Input caret uses Action Blue.
- **Content:** muted placeholders, full available width and resizable textareas.
- **Error:** a separate red validation summary. No custom invalid-field or disabled-field visual treatment is established by this stylesheet.

### Navigation

The rail uses Ink with Rail Text links. Each item is a text-and-SVG row with a minimum height (44px). Current destination uses Rail Selected fill, Paper text and semibold weight; hover has a darker blue-slate fill. The shared keyboard outline remains visible.

On narrow screens, a labelled Menu / Close menu control reveals navigation. The source closes it on route changes and handles Escape by returning focus to the menu control. This describes source behavior; keyboard acceptance remains open.

### Queue Filters and Record Rows

Filters are plain buttons with a neutral count chip. The selected filter uses Action Blue text and a bottom indicator; its state is exposed with `aria-pressed`. Record rows align the reference and subject, owner, textual state, due date and next action. An explicit link opens the record.

The wide record grid collapses through the Layout breakpoints. The source uses a subtle hover wash and changes subject-link color on hover. The queue context states its sort order; this source document does not validate backend ordering.

### Notices and Disclosures

Notices combine an inline information SVG, plain text and a pale semantic background inside a thin border. Amber notices and red validation summaries provide specific status variants.

Native `details` / `summary` controls disclose demo credentials and secondary options. Their summary is a visible semibold text action with the shared focus outline. Disclosure is immediate; no animation is introduced.

## Do's and Don'ts

### Do:

- **Do** keep responsibility, status and next steps readable as separate facts in a record.
- **Do** use the source tokens for shared colors, control corners and panel corners.
- **Do** preserve visible keyboard focus and text labels for interactive controls.
- **Do** allow content and control labels to wrap, and use the implemented responsive grids.
- **Do** keep secondary options in disclosures when the primary task can remain visible.
- **Do** retain clear student-prototype and fictional-data identification.

### Don't:

- **Don't** use semantic status colors as decoration or omit the words that explain them.
- **Don't** add ornamental stationery textures, raster hero imagery or decorative animation to this operating workspace.
- **Don't** replace the system sans hierarchy with a separate display typeface.
- **Don't** hide the owner or next step behind an icon-only action.
- **Don't** treat generated preview ramps or this source inventory as approval of rendered appearance.
